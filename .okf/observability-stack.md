# What it deploys

Stack `jaypee-solutions/observability/prod`, source `services/observability`, namespace `observability`, 21 resources at first apply plus a Longhorn NetworkPolicy. Design and alternatives are in ADR-0019. Components: Loki (single binary, 10 GiB Longhorn PVC), Mimir distributed on one node with blocks in the QuObjects bucket `mimir-metrics` (bundled MinIO, ruler and Alertmanager disabled), Grafana, Alloy (one Deployment), kube-state-metrics, node-exporter. All state volumes are Longhorn PVCs and therefore join the nightly `default` recurring backup group.

Grafana is at `https://g.4jp.de` (Traefik IngressRoute, wildcard certificate, dnsmasq host record `g` pointing at `10.10.88.1`). `grafana.4jp.de` is a public Cloudflare record for the user's old Grafana at `192.168.178.125`, which is why `g` is used. The admin password is a Pulumi-generated secret: `kubectl -n observability get secret grafana -o jsonpath='{.data.admin-password}' | base64 -d`. The workstation resolver uses `1.1.1.1`, which cannot resolve LAN records such as `g.4jp.de`; use the router resolver or `curl --resolve g.4jp.de:443:10.10.88.1`.

# Alerting

Alert rules, the normal Pushover contact point, the emergency contact point, the notification policy and dashboards are provisioned from code (`alert_rules.py`, `grafana.py`, `dashboards.py`); nothing is click-operated. The normal contact point stays at priority 0. A child policy routes `severity=critical` to `pushover-emergency` (priority 2, retry 60 seconds, expire 3600 seconds, resolved priority 0); warning is the default, and the 12-hour repeat interval is unchanged. The 14 critical rule UIDs are `node-not-ready`, `longhorn-volume-unhealthy`, `longhorn-backup-target-unavailable`, `longhorn-volume-backup-stale`, `cnpg-instance-down`, `cnpg-wal-archiving-failing`, `cnpg-backup-stale`, `paperless-backup-stale`, `mimir-samples-discarded`, `tandoor-down`, `netbox-down`, `certificate-expiring`, `probe-failing`, and `probe-failing-slow`. See ADR-0032. Severity is the rule-level tuning mechanism.

Rules added 2026-10-19 (22 in total; each expression was run against live data first): `mimir-samples-discarded` (`increase(cortex_discarded_samples_total[10m]) > 0` per reason, 10 minutes, critical; replayed against 2026-10-18 it reads 1 at 17:00 and 18:20 UTC and 0 at 19:00, so it would have paged within the first quarter of an hour of the label-limit loss), `tandoor-down` (`up{job="tandoor"} == 0`, alerts also without data, because `Scrape target down` cannot fire when the pod and its `up` series are gone) and `tandoor-server-errors` (5xx above 0.05 per second for 10 minutes). Tandoor's backups need no own rule: `cnpg-backup-stale` covers every cluster and `longhorn-volume-backup-stale` every volume.

Test a receiver with `POST /apis/notifications.alerting.grafana.app/v1beta1/namespaces/default/receivers/<base64 name>/test` (the legacy `/api/alertmanager/.../receivers/test` returns 410). The body is `{"integration": {uid, type, settings}, "alert": {...}}`; for provisioned receivers, include secrets in `settings` (`secureFields` alone returns `user key not found`). Do not send a `version` for Pushover: Grafana rejected version `1` as invalid. The test on 2026-10-13 returned `success`.
On 2026-10-24 the provisioning API showed both contact points and the `severity=critical` route, and all 24 rules reported `health=ok`. The current v1beta1 receiver-test API returned HTTP 200 with `status: success`; user confirmation that the emergency notification repeats until acknowledged is pending.

Alerting cannot report its own failure: if Grafana, Alloy or Mimir is down, nothing pages.

# Dashboards

Nine dashboards in the Grafana folder `Homelab`, provisioned from code. Five are generated by `dashboards.py`: Cluster overview, Backups and storage, Kubernetes workloads (namespace variable), Observability self-health (Mimir, Loki and Alloy ingestion, errors, object store failures, last block upload; the place to see the monitoring pipeline fail) and Logs explorer (Loki, namespace, pod and search variables). Four are community dashboards vendored unchanged under `assets/grafana/dashboards/` and adapted when rendered (datasource inputs and variables pointed at the `mimir` datasource, datasource variables removed): Node Exporter Full (grafana.com 1860 rev 101), CloudNativePG (20417 rev 4), Longhorn Monitoring and Backups (16888 rev 35) and Traefik Official Kubernetes (17347 rev 7). The donors' dashboards (Authentik, Hetzner Storage Box, PBS sync, Restic, Synology) are specific to services JP does not run, and a QNAP counterpart would need an snmp-exporter, so it was not added.

Against live data: Node Exporter Full has data on 111 of 124 panels (no systemd collector, fans or power supply), Longhorn on 33 of 34, CloudNativePG on 56 of 67, Traefik on 11 of 14 (rate panels need recent traffic). The remaining CloudNativePG gaps are expected: replication lag (single instance), tablespaces, First Recoverability Point (Barman plugin leaves the metric at 0), CPU and memory utilisation (they divide by resource requests the pilot does not set) and Ready Operator Pods (its pod-name regex does not match `cloudnative-pg-*`). The dashboard's kube-prometheus recording rule `node_namespace_pod_container:container_cpu_usage_seconds_total:sum_irate` does not exist here, so the adapter replaces it with the raw cAdvisor `irate` expression. The dashboards ConfigMap is about 445 KB of the 1 MiB limit, so check the size before vendoring more. Evaluate a new dashboard's queries against live data before adopting it; many panels read empty when a variable or label does not match.

# Syslog from the QNAP

Decision and alternatives: ADR-0024. Alloy listens on four ports, 1514 for RFC 5424 and 1515 for RFC 3164, each over TCP and UDP (Alloy needs one listener per format). The Service `alloy-syslog` publishes them on the fixed MetalLB address `10.10.88.2` (local DNS `syslog.4jp.de`) with `externalTrafficPolicy: Local` and `loadBalancerSourceRanges` limited to the QNAP's NICs `10.10.0.10` and `10.10.0.6`. Loki gets `{job="qnap-syslog", source="qnap"}` plus `host`, `app`, `severity`, `facility` and `source_ip`; the timestamp is the arrival time.

On the QNAP (QuLog Center, Log Sender, Send to Syslog Server): enable it and add a destination with host `syslog.4jp.de`, port 1514 and protocol TCP, log types event and access, format RFC 5424 (use port 1515 for RFC 3164). If nothing arrives, the QNAP is probably sending from an address outside the allowed range: widen `alloy.syslog.allowed-sources` in `services/observability/Pulumi.prod.yaml`.

Verified 2026-10-17 with test messages: RFC 5424 and RFC 3164, over TCP and UDP, all four arrived in Loki with the labels above (0 parse errors); a sender outside the range could not connect. Test with a busybox pod against the Service (`nc -w2 alloy-syslog 1514` with `printf '<14>1 <ISO time> host app 1 ID - message\n'`, and `nc -u` for UDP); in Loki query `{job="qnap-syslog"}`. Pitfalls found: the Alloy chart's `extraPorts` list only the TCP ports on the chart's own Service (a same-numbered UDP entry is dropped), so test through `alloy-syslog`, which carries both; and the workstation cannot test the LoadBalancer address, because it is deliberately not an allowed source.

Real QNAP messages arrive from `10.10.0.6` as host `qnap`, app `qulogd:` (the colon is part of the tag). **Node ports bypass `loadBalancerSourceRanges`:** kube-proxy applies the source ranges to the load balancer address only, so a node port on `10.10.8.1` accepted a message from the workstation. The Service now has `allocateLoadBalancerNodePorts: false`; that flag does not release ports that are already allocated, so the Service was recreated (`delete_before_replace`, as its name and address are fixed). Check with `nc -z <node> <former nodePort>` from a host that is not allowed.

# Probes and scrapes of external targets

Decisions: ADR-0025 and ADR-0026. **Applied 2026-10-17.** The legacy Prometheus' internet-facing probes (27 `http`, 1 `slow`, 3 `icmp`, 2 `tcp`) and its `ax51` (3 HTTPS endpoints) and `pretix` scrapes now run in Alloy. The targets are not in the repository, because it is public and about 20 probed sites are customer domains: the Secure Note `Monitoring Targets` holds one `<group> <target>` per line, the Logins `Prometheus AX51 Scrape` and `Prometheus Pretix Scrape` the basic-auth credentials. `targets.py` parses the note strictly and writes the Secret `alloy-targets` (fixed name, mounted at `/etc/alloy-targets`); `config.alloy` reads it with `discovery.file` and `local.file`, so a changed note reaches Alloy within about a minute without a restart. Probe series keep the legacy shape: `instance` is the probed address and `job` is `blackbox`, `blackbox-slow`, `blackbox-icmp` or `blackbox-tcp`. The helper `/tmp/create-monitoring-items.sh` (not in the repository) builds the items from the legacy Ansible vault without printing a value.

Verified: all 33 probes succeed (27 `blackbox`, 1 `blackbox-slow`, 3 `blackbox-icmp`, 2 `blackbox-tcp`), **ICMP works from a pod without extra privileges**, 27 certificate-expiry series exist, `ax51` (3 of 3 endpoints) and `pretix` are `up`, `wordpress_core_*` and `pretix_*` series arrive, and the three new Grafana rules (`probe-failing`, `probe-failing-slow`, `probe-certificate-expiring`) are `inactive`. Since every legacy rule was inactive on the same day, every legacy probe was succeeding too, which matches. Pitfalls: the first apply failed on the node's inotify limit (see the lessons file; the limit is now 1024), and `prometheus.scrape` takes its `job` from the component name unless `job_name` is set, so `ax51` and `pretix` first appeared as `prometheus.scrape.ax51` and `prometheus.scrape.pretix`.

Series budget (ADR-0026): Mimir allows 150,000 active series per tenant. The API server job alone held 82,727, of which about 66,000 were histogram buckets that nothing uses; Alloy now drops every `apiserver` `_bucket` series (a `prometheus.relabel` before the remote write). After a flush of the ingester head (`POST /ingester/flush?wait=true` on `mimir-ingester-0`, HTTP 204) the series in memory fell from 150,000 to 88,090, and 113,790 once the probes and scrapes were in. Check `cortex_ingester_memory_series` before adding the LAN targets.

The 1Password resolver reads a Secure Note through the field `note_value`; the provider has no `notes` attribute, which the resolver once listed by mistake.

# Tandoor

Decision: ADR-0028. Alloy scrapes `tandoor.tandoor.svc:80/metrics` every 30 seconds as job `tandoor` (django-prometheus, enabled with `ENABLE_METRICS=1`); applied 2026-10-18, `up{job="tandoor"} == 1`, 261 series and growing with the views that are used. The endpoint is unauthenticated, so Tandoor's IngressRoute does not route `/metrics` and the Service name is in Tandoor's `ALLOWED_HOSTS` (Django rejects other Host headers, and a pod-IP scrape would get a 400). `Scrape target down` covers the job.

Dashboard `Tandoor` (uid `homelab-tandoor`, generated, 17 panels): scrape up, requests per second, responses by status, 5xx, request latency p50/p95/p99, top views by rate and by mean latency, records created per hour by model, CPU, memory against the 1 Gi limit (PDF export runs a browser), restarts, media volume use, database size, the age of the last CloudNativePG backup and of the last Longhorn backup of `mediafiles`, error count and the log. Findings from validating it against live data: Tandoor's overall latency histogram (`django_http_requests_latency_including_middlewares_seconds`) never counts a request, so the quantiles use the per-view histogram summed by bucket (17 buckets per view and method, a few thousand series at most); an idle view divides by zero in a mean (`+Inf`), so the denominator is filtered with `> 0`; the Longhorn backup age panel shows no data until the first nightly backup instead of "56 years" (`longhorn_volume_last_backup_at` is 0 for never).

# Docker containers dashboard

Dashboard `Docker containers` (uid `homelab-docker-containers`, generated, variables `stack` and `name`, 19 panels; ADR-0036) for the Docker hosts outside the cluster, from the cAdvisor of the `ax51` job (71 running containers on 2026-10-25). Layout: host CPU, memory and load per core plus running, restarted and OOM-killed containers as stat tiles; a ranking table of every container over the selected range (CPU as share of the 16 host cores, memory, memory of limit, network, CPU pressure; names link to the filter variables); CPU and memory by container (top 10 by mean over the range, legend table sorted by mean) and by Compose stack (stacked); then top-5 panels for CPU wait, throttling, memory against limit, memory pressure, network in/out and threads, and the shortest uptime. Only cAdvisor series carry the `name` label, so the selector (`name!=""`) leaves the node exporter and Docker engine targets of the same job out. The `container_label_*` labels are gone since the label fix (ADR-0026); Alloy keeps the Compose project as `stack` (the container name for containers without Compose; series before 2026-10-25 have none, the variable's All value is `.*`). Host-network containers (`minecraft-minecraft-1`, `node-exporter`, mailcow netfilter) report every host interface, so network panels select `interface=~"eth[0-9]+"` and leave them out. There is no per-container disk I/O (no blkio or filesystem series) and `container_pressure_io_*` is 0 for every container, hence no disk panel. 16 dashboards in total, 501 KB of the 1 MiB ConfigMap limit.

`container_network_advance_tcp_stats_total` (AX51 cAdvisor, found 2026-10-18): cAdvisor's advanced TCP statistics, enabled only when the `advtcp` metric set is switched on in that cAdvisor [INFERENCE: it is off by default in current cAdvisor]. Each series is one kernel TCP counter of one container's network namespace, taken from `/proc/<pid>/net/netstat` and `net/snmp` (the TcpExt and Tcp counters), in the label `tcp_state` (misnamed: the values are counter names such as `delayedacks`, `tcptimeouts`, `tcpsynretrans`, `tcphphits`, `passiveopens`, `prunecalled`, `tcpsackrecovery`, `rcvpruned`, `tcpmd5failure`). There are 99 counters per container, so 79 containers give about 7,800 live series, which is nearly half of the `ax51` job (about 17,000). It is useful for diagnosing TCP retransmissions and timeouts of one container; nothing in this repository uses it (no panel, no rule). The counters of containers on the host network repeat the host's values. If the series budget gets tight, drop the family in the `ax51` relabel, or keep only the few counters that matter, for example `tcpsynretrans` and `tcptimeouts`.

Verified: both jobs up, 0 endpoint errors, about 970 new series (Mimir 100,666 of 150,000), synthetic IPv4/IPv6 filterlog lines parsed as intended, real lines arrive from `10.10.0.1`, every dashboard panel returns data (WireGuard handshake is a Unix timestamp; `opnsense_firewall_*_packets` are monotonic counters, `rate()` works), rules `ok`/`inactive`. # Pitfalls found

- **Longhorn ships NetworkPolicies** (`longhorn-system`, chart 1.13) that admit only Longhorn pods to the manager, so Alloy, a probe pod and the API server proxy all got `connection refused` on port 9500. `longhorn_access.py` adds an additive policy letting only Alloy reach port 9500.
- **Longhorn 1.13 metric shapes differ from older docs.** `longhorn_volume_robustness` is a 0/1 series per `state` label (not a 0-3 enum); there is no `longhorn_backup_state`; backup freshness is `longhorn_volume_last_backup_at` (0 means never) and `longhorn_backup_target_status{condition="unavailable"}`. A rule written from older docs, `> bool 1`, could never fire and would have looked healthy. Always evaluate a new rule against live data.
- **The Barman plugin does not populate CloudNativePG's backup metrics** (`cnpg_collector_last_available_backup_timestamp` stays 0). Backup freshness comes from kube-state-metrics custom-resource metrics `cnpg_backup_stopped_at_seconds{phase}` over the `Backup` objects.
- **nginx gateways name their proxy port `http-metrics`** (Loki and Mimir), which the generic port-name scrape rule would hit and report as `up == 0`; the Alloy config drops containers named `gateway` or `nginx`.
- **The old `grafana/grafana` chart repository is deprecated**; use `grafana-community.github.io/helm-charts` (chart 13.x).
- **Never set `pod` or `namespace` target labels on a scrape whose series describe other objects.** The kube-state-metrics relabel did, which renamed the real pod label to `exported_pod` and broke every pod-keyed query and alert text (found when a community dashboard returned nothing). Fixed 2026-10-15; history before then still has `exported_pod`.
- **Mimir rejects series with more than 30 labels, and Alloy drops the whole batch.** cAdvisor on a Docker host exposes every container label as `container_label_*`; the AX51 containers had 33 to 36 labels per series (`err-mimir-max-label-names-per-series`, HTTP 400), and each rejected write cost a batch of 2,000 samples (about 1% of everything, from 2026-10-17 17:11 UTC until the fix on 2026-10-18 18:26 UTC). The `ax51` scrape drops `container_label_.+` (ADR-0026, update 2026-10-18). Look for it with `kubectl -n observability logs deploy/alloy -c alloy | grep non-recoverable` and `cortex_discarded_samples_total{reason="max_label_names_per_series"}`; Alloy's own log is the only place that shows it, because no alert watches the discard counter (follow-up).
- **`topk` in a range query ranks per step**, so a 6 h chart collects far more than k lines (29 for `topk(15, …)` on AX51 CPU). Rank over the range instead: `(expr) and on (name) topk(k, avg_over_time((expr)[$__range:$__interval] @ end()))` (ADR-0036; `@ end()` works in Mimir).
- `longhorn-volume-backup-stale` stays pending for 26 hours on a brand-new volume (its backup timestamp is 0 until the first nightly job). The first scheduled run, 2026-10-14 02:00 UTC, completed backups for all five volumes (`Completed` Longhorn `Backup` objects, 02:00:06 to 02:02:32) and no alert fired. A restore from a scheduled backup passed on 2026-10-17 (see the platform note).

# Wazuh metrics and Mimir health alerts (ticket #96)

Alloy code defines three bounded jobs: `wazuh-indexer` scrapes `wazuh-indexer-exporter.wazuh.svc:9114`; `wazuh-agent-status` and `wazuh-high-level-events` query `wazuh-findings-exporter.wazuh.svc:7979/probe`. Its indexer allow-list retains `up`, cluster status/node/active/unassigned-shard gauges, `elasticsearch_indices_store_size_bytes_total` and `elasticsearch_indices_docs_total` only for `wazuh-*` indices, JVM heap used/max and filesystem available/size. The generic `metrics_pods` scrape excludes the Wazuh namespace and both exporter containers, preventing the exporters' broad default output from inflating cardinality. Use `sum` across retained Wazuh index labels for totals.

The findings exporter returns `wazuh_agent_status_count{status}` from a `status.keyword` terms aggregation over `wazuh-monitoring-*`, and `wazuh_high_level_events` from `wazuh-alerts-4.x-*`, filtered to `rule.level >= 12` in the last 15 minutes. No qualifying events yields zero. `metrics_reader` has document-read access only to `wazuh-*`; the indexer exporter needs metadata-only `indices:monitor/stats` on all indices for `/_all/_stats` and `/_cat/shards`; it has no document-write permission.
