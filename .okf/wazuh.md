# Wazuh security monitoring

**[User decision; deployed]** Single-node Wazuh deployment on k0s; host software inventory/vulnerability reporting is primary, with manual operator triage and no automated remediation. Architecture, implementation, decisions and terms: [[Wazuh Security Monitoring]], [[Wazuh Implementation Plan]], [[ADR-0037 - Wazuh security monitoring on k0s]], [[GLOSSARY]].

## Upstream 4.14.9 facts and pitfalls

- **[Verified (upstream)]** Official Kubernetes deployment uses Kustomize, with 3 indexers, manager master/workers and dashboard. Local-environment manifests include demo credentials/certificates, unpinned BusyBox, privileged `vm.max_map_count` init, MicroK8s storage class, and public load balancers. Adapt rather than apply as-is. https://github.com/wazuh/wazuh-kubernetes/tree/v4.14.9
- **[Verified (upstream)]** Security configuration changes require `securityadmin.sh`; default-init security files apply only at first start. https://documentation.wazuh.com/current/deployment-options/docker/wazuh-container.html
- **[Inference]** OpenSearch client certificates should use PKCS#8 keys and explicit DN matching.
- **[Verified (upstream)]** State indices include `wazuh-states-vulnerabilities-*` and inventory indices; vulnerability documents expose `vulnerability.detected_at`, severity, score and scanner condition. State indices have no `@timestamp` and no explicit fixed-version field. https://documentation.wazuh.com/current/user-manual/wazuh-indexer/wazuh-indexer-indices.html
- **[Verified (upstream)]** Wazuh 5.0 is a breaking migration with a new agent protocol/schema and migration tooling, not an in-place upgrade. https://github.com/wazuh/wazuh-kubernetes/blob/main/docs/ref/upgrade.md
- **[Verified (upstream)]** OPNsense plugin supports agent/event forwarding only; FreeBSD is not a vulnerability-detection vendor feed. QNAP has no Wazuh agent in this plan. https://docs.opnsense.org/manual/wazuh-agent.html ; https://documentation.wazuh.com/current/user-manual/capabilities/vulnerability-detection/compatibility-matrix.html
- **[Verified (upstream)]** Trivy v0.69.4 was affected by a supply-chain compromise; planned chart bundles 0.75.0. https://github.com/advisories/GHSA-69fq-xp46-6x23
- **[Verified (upstream)]** pyToshka Wazuh Prometheus exporter is stale (last push 2025-07-04; no releases); reject it. `json_exporter` supports POST bodies, HTTP client auth/TLS and JSONPath. https://github.com/pyToshka/wazuh-prometheus-exporter ; https://github.com/prometheus-community/json_exporter

## Integration decision

**[User decision]** Grafana queries OpenSearch for current findings and Mimir for aggregate trends/health. Loki receives selected vulnerability transition events and manager feed logs; Wazuh alert indices remain authoritative. New Active Critical events are grouped per agent for five minutes and delivered through a separate Loki Grafana alert rule to normal Pushover. Delivery is best-effort; state and event history are distinct. Trivy covers k0s workload images only; Wazuh dashboard remains necessary for agent management, IT Hygiene, SCA, FIM, rule/decoder testing and API console. All new Grafana alert rules based on Wazuh data start at warning; promotion requires reviewed evidence after about two weeks. Wazuh detection-rule levels are a separate scale.

## Vulnerability events and CTI health

- **[Verified (upstream)]** Wazuh 4.14.9 package-delta alerts use `data.vulnerability.status` (`Active`/`Solved`), CVE and package identity, with agent identity and top-level alert `timestamp`; rules 23502–23506 cover solved and active severities. https://github.com/wazuh/wazuh/blob/v4.14.9/ruleset/rules/0520-vulnerability-detector_rules.xml ; https://github.com/wazuh/wazuh/blob/v4.14.9/src/wazuh_modules/vulnerability_scanner/src/scanOrchestrator/eventPackageAlertDetailsBuilder.hpp
- **[Verified (upstream)]** Events are not a complete lifecycle ledger: initial inventory/sync and some rescans do not emit transitions; hotfix resolution may identify “one or many packages.” Treat the vulnerability state index as authoritative and events as best-effort notifications. https://documentation.wazuh.com/4.14/user-manual/capabilities/vulnerability-detection/how-it-works.html
- **[Verified (upstream)]** The manager writes plain-text logs to `/var/ossec/logs/ossec.log`; scanner logs include `Feed update process completed.` and `Error updating feed: ...`. **[Inference]** A read-only sidecar can tail this file via the manager `logs` volume and send lines to Loki. Warn on explicit errors or no success observed for two hours; absence alone does not prove failure. https://documentation.wazuh.com/4.14/user-manual/reference/ossec-conf/logging.html ; https://github.com/wazuh/wazuh/blob/v4.14.9/src/wazuh_modules/vulnerability_scanner/src/databaseFeedManager/databaseFeedManager.hpp
- **[Verified (upstream)]** The API exposes manager logs, but `manager:read` is broader than the single logs endpoint; no native feed-freshness Prometheus metric was verified. The chosen sidecar avoids API credentials and that broader RBAC scope. https://documentation.wazuh.com/4.14/user-manual/api/rbac/reference.html
- **[User decision]** Debian-family agents only initially; k0s0 is the stop/go pilot; only explicitly approved hosts are added. Proxmox coverage is partial. OPNsense event forwarding is included as non-blocking manual tier-3 integration, without CVE coverage. Authentik SAML is optional post-core with local break-glass login.

## Wazuh workspace (ticket #87)

- Added `services/wazuh` as a Pulumi workspace with production defaults for Wazuh 4.14.9, namespace `wazuh`, dashboard and agent hostnames, the selected MetalLB address, and indexer/manager sizing.
- Pulumi TLS creates an internal RSA CA in Secret `wazuh-ca`; cert-manager uses Issuer `wazuh-ca`. Leaf Certificates are named and write matching Secrets: `wazuh-indexer`, `wazuh-admin`, `wazuh-filebeat`, `wazuh-manager`, `wazuh-dashboard`, `wazuh-grafana-reader` and `wazuh-metrics-reader`. Each leaf uses RSA PKCS#8 keys with automatic renewal; the CA PEM is exported for Grafana.
- Chosen certificate DNs (subject common name only): `CN=wazuh-indexer` (indexer node), `CN=wazuh-admin` (indexer administrator), `CN=wazuh-filebeat` (manager/Filebeat client), `CN=wazuh-manager` (manager service), `CN=wazuh-dashboard` (dashboard), `CN=wazuh-grafana-reader` and `CN=wazuh-metrics-reader` (read-only clients). Ticket #88 must use these exact DNs in its security configuration.
- Pulumi-generated passwords and bcrypt hashes are kept in Secret `wazuh-credentials`. `internal_users.yml` contains only generated `admin`, `kibanaserver`, `grafana_reader` and `metrics_reader`; no upstream demo users. The Secret also contains API and enrollment credentials. Indexer roles and mappings are applied by the #88 security Job.
- Applied and verified: preview proposed the namespace, CA Secret, issuer, leaf Certificates and credentials only; all Certificates reported `Ready=True`; all leaf Secret keys passed `openssl pkey`; all four rendered user hashes validated against their generated passwords. `uv run ./scripts/run-all-checks.sh` passed.

## Indexer (ticket #88)

- `wazuh-indexer` is a single StatefulSet running `wazuh/wazuh-indexer:4.14.9`, with a 2 Gi heap, 500m CPU / 3 Gi memory requests, 4 Gi memory limit and a 50 Gi Longhorn PVC. The PVC requests the `default` recurring-job group used by the cluster's nightly Longhorn backup. No privileged init container is used; the indexer Pod runs as UID/GID 1000 with `fsGroup: 1000`.
- The `wazuh-indexer` ClusterIP Service exposes HTTPS on 9200 (`wazuh-indexer.wazuh.svc:9200`). Indexer certificates use Secret `wazuh-indexer`; administrator jobs use `wazuh-admin`; the CA is in `wazuh-ca`. The configured node/admin DNs are `CN=wazuh-indexer` and `CN=wazuh-admin`.
- The Job seeds the full bundled OpenSearch Security config, replaces its internal-user and node-DN files with generated/code-managed values, applies the Grafana/metrics reader roles and mappings through the Security API, and installs replica-zero templates and ISM policies (60-day alerts; 30-day monitoring/statistics). The Job name hashes rendered security settings and policy payloads.
- Grafana reads through generated user `grafana_reader` (role `wazuh_grafana_reader`, certificate Secret `wazuh-grafana-reader`). Manager Filebeat authenticates with generated `admin` (password key `admin` in Secret `wazuh-credentials`) and client certificate Secret `wazuh-filebeat`; no distinct Filebeat user is defined. Its 4.14.9 client requires `compatibility.override_main_response_version: true` in the 2.19.6 indexer config.
- **Live acceptance:** manager-side Filebeat negotiated as 7.10.2, loaded the native `wazuh` template and connected without the initial `_type` bulk error. Indexer indices included `wazuh-alerts-4.x-2026.10.28`, `wazuh-states-vulnerabilities-wazuh-manager-0`, and manager inventory indices.

## Manager (ticket #89)

- `wazuh-manager` is a standalone one-replica StatefulSet running `wazuh/wazuh-manager:4.14.9`. It requests 500m CPU and 1536Mi memory, with a 3Gi memory limit and no CPU limit. Its 20Gi `manager-data-wazuh-manager-0` claim and Longhorn Volume carry `recurring-job-group.longhorn.io/default=enabled`.
- The PVC persists `/var/ossec/etc` (including `client.keys`), logs, queue, API configuration, Filebeat state/configuration, and the upstream manager data directories. An init container seeds shipped manager/API configuration into the initially empty PVC only when the corresponding defaults are absent; another initializes the manager indexer connector keystore.
- `wazuh-manager` is the ClusterIP API service on 55000; `wazuh-manager-internal` is the ClusterIP agent/enrollment service on 1514/1515; `wazuh-manager-headless` is the StatefulSet identity service. `wazuh-manager-agents` is the LoadBalancer service at `10.10.88.3`, TCP 1514/1515, with source ranges `10.10.0.0/16` and `192.168.178.125/32` and `externalTrafficPolicy: Local`. Cloudflare A record `wazuh-manager.4jp.de` targets `10.10.88.3`.
- Vulnerability Detection is enabled; manager inventory uses `https://wazuh-indexer.wazuh.svc:9200` with TLS. API user `wazuh-wui` uses key `api` in `wazuh-credentials`; enrollment key `enrollment` is mounted at `/var/ossec/etc/authd.pass`. Filebeat and the vulnerability connector use indexer user `admin` (key `admin`) and client certificate Secret `wazuh-filebeat`; CA Secret `wazuh-ca`.
- `alerts-tail` reads `/var/ossec/logs/alerts/alerts.json`; `ossec-log-tail` reads `/var/ossec/logs/ossec.log`. Both expose the files through read-only log mounts and stdout.

The user has only `cluster_monitor` and `read` on `wazuh-*`; a live PUT returned HTTP 403. Exporters are internal-only; no Alloy scrape configuration is included (#96).
