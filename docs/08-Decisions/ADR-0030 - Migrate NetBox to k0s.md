# ADR-0030 - Migrate NetBox to k0s

## Status

Accepted on 2026-10-20. The Pulumi stack is applied and the legacy data is imported; the cutover is recorded in `.okf/netbox.md`.

## Context

NetBox is the inventory this repository and the agent use (`nbcli`, the `k0s0` records). It ran on `dockerhost` as four containers in `/opt/netbox` (netbox-docker 3.2.0, NetBox 4.2.8, PostgreSQL 17.11, one cache Valkey, no worker, no task Valkey), and **`dockerhost` has no backup** ([[ADR-0028 - Migrate Tandoor to k0s]]). A verified safety copy (`pg_dump -Fc` plus the configuration files) was taken first on 2026-10-20. The legacy instance has 13 devices, 63 interfaces, 49 IP addresses, one superuser and two v1 API tokens, no media files, no reports, no scripts, no plugins, no mail and no LDAP or SSO in use. The donor TH runs NetBox with the official chart; MP has none.

## Decision

- **The official Helm chart `netbox` (8.3.92, NetBox 4.7.3)** on a dedicated workspace `services/netbox` (stack `jaypee-solutions/netbox/prod`), instead of hand-written manifests: it is upstream-maintained and is what the donor runs. The Bitnami PostgreSQL and Valkey subcharts are not used.
- **The upgrade from 4.2.8 to 4.7.3 happens during the import.** Upstream allows direct upgrades within v4. The rehearsal with the safety dump proved the migrations (0 unapplied, all row counts equal); the stopped legacy instance and the safety copy are the rollback. No separate upgrade change.
- **Database: a dedicated CloudNativePG cluster `netbox-db`** from the shared helper (PostgreSQL 17, Barman plugin to its own prefix, daily 21:00 UTC, 14-day window), covered by `cnpg-backup-stale`. NetBox creates the trusted `ltree` extension itself because its user owns the database. The data moves as `pg_dump -Fc` and `pg_restore` into a recreated empty database, never `--clean` (see `.okf/tandoor.md`).
- **Valkey: one Deployment, database 0 for tasks and 1 for the cache, no persistence and no password**, cluster-internal like the Redis of Paperless. Both are rebuilt by NetBox.
- **Secrets are generated by Pulumi, none live in 1Password.** A new `SECRET_KEY` (only browser sessions end). The API token pepper is explicit, because the chart would generate it with Helm `lookup`, which does not work under `helm.v4.Chart`, so it would change on every render. The two v1 API tokens live in the database and keep working.
- **No superuser creation** (`SKIP_SUPERUSER`): the imported account is the only one. The chart still requires the secret `netbox-superuser`, so a generated one exists.
- **`loginRequired: true`**, as on the legacy instance; the chart default would allow anonymous reads. NetBox 4.7 logs that `LOGIN_REQUIRED` is deprecated and removed in v5.0 (follow-up).
- **Mail dropped** (no `ADMINS`, nothing sent). **CORS not carried over** (nothing uses the API cross-origin). **Reports and scripts are not persisted** (empty on the legacy instance). The housekeeping CronJob stays off: since 4.4 housekeeping is a system job in the worker.
- **Media volume `netbox-media`, 1 Gi** (Longhorn, default recurring group, backed up nightly); the legacy instance had no files, so uploads start here.
- **Metrics, alerts and dashboard.** `METRICS_ENABLED` is on; Alloy scrapes `netbox.netbox.svc:80/metrics` as job `netbox` (the Service name is in `allowedHosts`), and the IngressRoute does not route `/metrics`. Alerts `netbox-down` and `netbox-server-errors`, and the dashboard `NetBox`. The Granian metrics of the chart stay off.
- **No CPU limits** on any container, including the chart's init containers (the chart presets set one), which get explicit small resources.
- **Cutover by DNS.** `netbox.4jp.de` pointed at `dockerhost` through a public Cloudflare A record. The user changes it by hand to Traefik's address `10.10.88.1`; the stack then manages the record by import ([[ADR-0029 - Service names as Cloudflare A records]]).
- **The legacy instance is stopped, not deleted**; removing it is stage-2 work that needs the user's approval.

## Consequences

- The import is a manual runbook (`.okf/netbox.md`), done with the application scaled to zero so the migrations do not race the restore. The 4.2 to 4.7 migration took about two minutes at startup.
- **The final import used the safety dump of 2026-10-20 17:20** instead of a fresh dump after stopping the legacy instance: the user stated that nothing was changed in NetBox in between. Edits made on the legacy instance after that are not on k0s.
- `nbcli` keeps its URL and its v1 token. **v1 tokens are deprecated since 4.6 and removed in NetBox v5.0**: create a v2 token for `nbcli` before then (follow-up).
- Until HBS 3 runs, the QNAP holds the only copy besides the node's own disks (same exposure as every other service on the cluster).

## Alternatives considered

- Plain manifests for NetBox: more code to own, and the chart is upstream's supported path.
- A separate upgrade change after the move: two migrations of the inventory instead of one proven rehearsal, for a 26 MB database.
- Carry the old `SECRET_KEY` over from `dockerhost`: ends no session worth keeping and needs a secret in the repository or 1Password.
- Chart-managed Bitnami PostgreSQL or Valkey: would bypass the CloudNativePG backups.
